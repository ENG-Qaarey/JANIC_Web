# Community Services Module

Allows external organizations to request technology, innovation, research, and training
services from JANIC. Supports **for-profit** and **nonprofit** organization types with
dynamic, type-specific form fields.

## Database

### Enums
- `OrgType` — `FOR_PROFIT`, `NONPROFIT`
- `OrganizationCategory` — 8 values (private company, startup, NGO, CBO, educational institution, foundation, youth org, other)
- `FundingStatus` — funded / partially funded / seeking funding / undetermined
- `ServiceRequestStatus` — 8 values (see workflow)
- `ServiceRequestPriority` — `LOW`, `MEDIUM`, `HIGH`, `URGENT`

> The enum is named `OrgType`, **not** `OrganizationType`, because a model named
> `OrganizationType` already exists (partnership org types). Prisma rejects the collision.

### Models
- `ServiceCategory` → has many `Service`
- `Service` → belongs to `ServiceCategory`
- `ServiceRequest` → belongs to `ServiceCategory` + `Service`; has many `Note`, `Attachment`, `History`
- `ServiceRequestNote`, `ServiceRequestAttachment`, `ServiceRequestHistory`

Relation fields on `ServiceRequest` are named `serviceCategoryRef` / `serviceRef` because
the scalar FK columns `serviceCategoryId` / `serviceId` occupy the obvious names.

Indexes: `status+createdAt`, `organizationType+status`, `serviceCategoryId+status`,
`assignedToId+status`, `requestNumber`.

### Request numbers
Format `JANIC-CS-<year>-<0000>`, generated by finding the highest existing number for the
current year. Note: this is **not** collision-safe under heavy concurrency — two requests
in the same millisecond can compute the same number, and the `requestNumber` unique
constraint will reject the second. The `id` is a cuid so no row is lost; the client just
retries. Swap for a database sequence or retry-on-`P2002` if volume grows.

`priority`, `search`, `page`, `limit`.

Added to `MODULES` in `lib/permissions/capabilities.ts`, generating
`community_services:{create,read,update,delete}`.

| Role | Capabilities |
|---|---|
| ADMIN | All (hardcoded bypass) |
| EDITOR | read, create, update, delete |
| STAFF | read |
| USER | none |

Sidebar entries are gated by `hasCapability(user, "community_services:read")`, so staff
without the capability never see the nav item. The API enforces the same capability
server-side via `hasPermission`.

## Status workflow

Transitions are validated server-side in `STATUS_TRANSITIONS`:

```
SUBMITTED            → UNDER_REVIEW | ADDITIONAL_INFO_REQUIRED | REJECTED | CANCELLED
UNDER_REVIEW         → APPROVED | ADDITIONAL_INFO_REQUIRED | REJECTED | CANCELLED
ADDITIONAL_INFO_REQUIRED → UNDER_REVIEW | REJECTED | CANCELLED
APPROVED             → IN_PROGRESS | CANCELLED
IN_PROGRESS          → COMPLETED | CANCELLED
COMPLETED / REJECTED / CANCELLED → (terminal)
```

`reviewedAt` is stamped on first entry to `UNDER_REVIEW`; `completedAt` on `COMPLETED`.
Every transition writes a `ServiceRequestHistory` row.

## Form behaviour

Four sections: Organization Information → Requested Service → Type-Specific Questions →
Declaration. Selecting For-Profit vs Nonprofit swaps the conditional block while
**preserving** previously entered values (state is a single object; hidden fields are
retained, not cleared). Category and Service are dependent selects — the service list is
filtered by the chosen category. Success state only renders after the server confirms
persistence; the form is not cleared on failure.

## Known gaps

These are real limitations of what is implemented, not oversights to ignore:

1. **No rate limiting.** The public `POST /api/community-services` endpoint is
   unthrottled, as are all other public POST routes in this project. The prompt asked for
   rate limiting on submission endpoints; the project has no rate-limit infrastructure at
   all, so none was added rather than introducing a new dependency.
2. **`/stats` is unauthenticated** and exposes aggregate counts to anyone. Needs
   `community_services:read`.
3. **No duplicate-submission protection.** No idempotency key; a double-click could create
   two rows (the button disables on `submitting`, but that is client-side only).
4. **No CSRF protection** on state-changing endpoints — consistent with the rest of the app.
5. **Attachments are not wired to a route.** `ServiceRequestAttachment` and the validation
   helper (`addAttachment`, MIME + 10MB allowlist) exist, but there is no upload endpoint
   and no form field. The form does not collect files yet.
6. **No notification dispatch.** JANIC has no notification infrastructure (only
   count badges computed in layouts). Nothing was invented. The admin notification count
   in `app/admin/layout.tsx` was **not** extended to include new service requests.
7. **`assignedToId` is not a real FK** to `User` — it is a plain string, so assignment is
   not referentially enforced. The UI has no assignee picker; assignment is API-only.
8. **Search is case-sensitive** on MySQL with the default collation used here.
9. **No CSV export** of request data.
10. **No 403 guard on the admin/staff pages themselves** — protection comes from the parent
    layout plus API-level capability checks, matching how every other admin page behaves.
